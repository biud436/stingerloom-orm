# 2.0 업그레이드

1.x는 무언가 잘못되어도 대부분 문제를 제대로 알리지 않았습니다. 예를 들어 오타가 난 컬럼 이름은 드라이버까지 그대로 전달되어 알아보기 힘든 에러로 이어졌습니다. 없는 행에 `save()`를 호출해도 성공했다고 응답했습니다. 배치로 삽입한 시각은 밀리초가 잘렸습니다. 2.0은 이런 경우를 찾아 실패를 실패로 알리도록 바꾼 릴리스입니다.

대부분의 애플리케이션은 버전만 올리면 업그레이드가 끝납니다. 다만 그동안 문제를 덮고 있던 코드가 있었다면 이제 그 자리에서 에러가 납니다.

```bash
pnpm add @stingerloom/orm@2
```

## 업그레이드 전 점검

배포하기 전에 로깅을 켜고 테스트를 실행해 보세요. 2.0에서 바뀐 동작은 거의 모두 에러나 경고로 드러납니다. 그래서 테스트를 한 번만 실행해도 고칠 곳을 대부분 찾습니다.

```typescript
await em.register({ /* ... */, logging: true });
```

## 공개 API 변경

### 루트에서 가져오던 내부 심볼

1.x의 `@stingerloom/orm`은 모듈 전체를 다시 내보냈습니다. 그래서 심볼 673개를 패키지 루트에서 import할 수 있었습니다. 여기에는 `SchemaRegistrar`, `CascadeHandler`, `EntityManagerInternals` 같은 엔진 내부와 표현식 렌더링 함수, 내부 타입 가드가 포함되었습니다. 2.0부터는 공개할 심볼만 골라 하나씩 지정해 내보냅니다.

import가 해석되지 않는다면 원래 공개 API가 아니던 심볼입니다. 엔진 내부를 대신할 경로는 따로 두지 않았습니다. 꼭 필요한 쓰임새가 있다면 이슈로 알려 주세요. 공개 진입점은 `@stingerloom/orm`, `@stingerloom/orm/nestjs`, 다이얼렉트별 서브패스로 이전과 같습니다.

### 직접 만든 드라이버

`ISqlDriver`에 `escapeIdentifier(name: string): string` 메서드가 추가되었습니다. 문서의 마이그레이션 예제는 예전부터 이 메서드를 호출했습니다. 하지만 이 메서드를 구현한 드라이버가 하나도 없었습니다. 그래서 예제를 그대로 복사하면 컴파일되지 않았고 런타임에도 실패했습니다. 내장 드라이버 세 개는 이미 이 메서드를 구현합니다. 직접 만든 드라이버라면 아래처럼 구현하면 됩니다.

```typescript
escapeIdentifier(name: string): string {
  return `"${name.replace(/"/g, '""')}"`;
}
```

### 메타데이터를 손으로 만드는 코드

`ColumnMetadata.name`과 `EntityScannerMetadata.name`이 선택 필드에서 필수 필드로 바뀌었습니다. 이 값은 실제로 항상 채워졌고 타입만 느슨했습니다. 그래서 영향을 받는 코드는 이 메타데이터 객체를 직접 만드는 커스텀 스캐너나 스키마 도구 정도입니다. 이런 코드는 이제 `name`을 반드시 채워야 합니다.

## 새로 던지는 예외

아래 상황은 1.x에서 에러 없이 잘못된 결과를 반환했습니다.

| 이런 코드 | 1.x | 2.0 |
| --- | --- | --- |
| 연결 `entities`에 없는 엔티티 | 첫 SQL 문에서 드라이버 에러로 실패 | 진입점에서 `EntityMetadataNotFoundError` |
| `where: { emial: "…" }` | 오타를 그대로 드라이버에 넘겨 "no such column" | 없는 컬럼을 짚고 가장 비슷한 이름을 제안하는 `InvalidQueryError` |
| `relations: ["autor"]` | 쿼리는 성공하고 관계만 `undefined` | 해석 가능한 관계 목록을 담은 `InvalidQueryError` |
| 기본 키에 해당하는 행이 없는 `save()` | 성공으로 응답하고 `afterUpdate`까지 실행 | `EntityNotFoundError` |
| `qb.where("status = 'open'")` | SQL 조각 전체를 컬럼 이름으로 취급 | `InvalidQueryError` |
| 표현할 수 없는 diff의 `migrate:generate` | `up()`이 TODO 주석뿐인 마이그레이션 생성 | 에러를 던져서 동작하지 않는 마이그레이션이 커밋되지 않게 함 |

이 중 두 가지는 조금 더 자세히 살펴볼 필요가 있습니다.

- **컬럼 이름 검증**: 검증기는 프로퍼티 이름, 데이터베이스 컬럼 이름, `@RelationColumn` 외래 키 섀도우, `@ComputedColumn` 이름, 단일 테이블 상속의 형제 컬럼을 받아들입니다. 거부하는 것은 엔티티가 매핑하지 않은 물리 컬럼입니다. 이런 컬럼은 예전에 검증 없이 통과해서 우연히 동작했습니다. 매핑하지 않은 컬럼으로 꼭 필터링해야 한다면 `@Column`으로 선언하세요. 아니면 `createQueryBuilder()`나 `em.query()`를 쓰세요.
- **없는 행에 `save()`**: `save()`를 "있으면 갱신, 없으면 삽입"으로 쓰고 있었다면 `upsert()`로 의도를 명확히 하세요. 행이 없을 가능성을 처음부터 전제한 코드라면 `exists()`로 먼저 확인하세요.

## 동작 변경

### `take: 0`은 이제 0건입니다

`limit: 0`도 마찬가지로 0건을 반환합니다. 1.x에서는 `0`이 falsy 검사에 걸려서 테이블 전체를 반환했습니다. 쿼리 빌더의 `qb.take(0)`은 처음부터 `LIMIT 0`이었으므로 이제 두 경로가 같게 동작합니다. 계산한 페이지 크기를 넘기는 코드가 "0이면 제한 없음"에 의존했다면 그 경우를 직접 처리해야 합니다.

### `stream()`이 지정한 범위를 지킵니다

`stream()`과 `streamBatch()`가 모두 해당합니다. 1.x에서는 내부 배치 로직이 호출자의 `limit`/`take`/`skip`을 덮어썼습니다. 게다가 `take`가 배치 크기보다 크면 같은 행이 다시 나왔습니다. 배치 크기 100에 `take: 150`을 주면 300건이 나왔고 그중 50건이 중복이었습니다. 이제는 지정한 범위가 스트림 전체의 범위입니다. `take`를 넘겼는데도 전체 행을 받던 코드는 이제 요청한 만큼만 받습니다.

### 시각 값이 저장되는 방식

1.x에서는 `insertMany`, `insertManyAndReturn`, `batchUpsert`와 `@CreateTimestamp`/`@UpdateTimestamp` 컬럼이 시각을 로컬 벽시계 문자열로 바꿔 저장했습니다. 이 문자열에는 오프셋도 밀리초도 없었습니다. 반면 `save()` 같은 단일 행 경로는 `Date`를 그대로 드라이버에 넘겼습니다. 그래서 한 컬럼 안에 두 가지 표기가 섞였습니다. 2.0부터는 모든 경로가 `Date`를 그대로 넘깁니다. 문자열로 바꾸는 일은 드라이버가 맡습니다.

- 배치로 삽입해도 밀리초가 남습니다. 다만 컬럼 정밀도가 밀리초를 지원해야 합니다.
- PostgreSQL `timestamptz`에서 배치 쓰기와 `save()`가 같은 시각을 저장합니다. 1.x에서는 애플리케이션 프로세스와 서버의 타임존이 다르면 두 경로가 저장하는 시각이 어긋났습니다.
- SQLite에 저장되는 문자열이 `2026-03-01 21:34:56`에서 `2026-03-01T12:34:56.789Z`로 바뀝니다.

읽기는 그대로입니다. ORM은 이전부터 두 표기를 모두 해석했으므로 이미 저장된 행의 의미는 달라지지 않습니다. 다만 직접 작성한 SQL이나 덤프 비교처럼 저장된 문자열을 그대로 비교하는 코드는 고쳐야 합니다. 자세한 내용은 [날짜와 타임존](./timezone.md)을 참고하세요.

### SQLite 소프트 삭제 시각

1.x에서는 SQLite의 `softDelete()`가 `datetime('now')`를 썼습니다. 이 함수는 UTC 시각을 만들지만 타임존 표기를 붙이지 않습니다. 그런데 ORM은 타임존 표기가 없는 문자열을 로컬 시각으로 해석합니다. 그래서 조회한 `deletedAt`이 프로세스 타임존의 오프셋만큼 어긋났습니다. 서울 타임존에서 실행하면 아홉 시간 이른 시각이 나왔습니다. 이제는 `Z` 표기를 붙여 저장하므로 올바르게 해석됩니다.

1.x에서 소프트 삭제된 행에는 옛 표기가 그대로 남아 있습니다. UTC가 아닌 환경에서 운영했고 그 시각을 삭제 여부 판별 이상의 용도로 쓴다면 [날짜와 타임존](./timezone.md#소프트-삭제-시각)의 보정 SQL을 한 번 실행하세요.

## 새 경고와 로그

### 에러 메시지에 해결 힌트가 함께 나옵니다

`suggestion`이 있는 에러는 그 문장을 `message` 끝에 `Suggestion: ...` 줄로 덧붙입니다. 그래서 메시지나 스택을 출력하는 로거라면 어디서든 해결 힌트가 보입니다. 에러 문자열을 정확히 비교하는 테스트는 고쳐야 합니다. `error.suggestion` 자체는 예전과 같습니다.

### 테넌트 컨텍스트가 없을 때

`tenantStrategy: "tenant_column"`을 쓰면서 `MetadataContext.run()` 밖에서 읽으면 1.x는 경고 없이 모든 테넌트의 행을 조회했습니다. 2.0은 엔티티 클래스마다 한 번씩 경고를 출력합니다. 정책은 아래처럼 직접 설정해 두세요.

```typescript
await em.register({
  // ...
  tenantStrategy: "tenant_column",
  tenantOnMissingContext: "throw", // "throw" | "warn"(기본) | "allow"
});
```

새로 작성하는 코드에는 `"throw"`를 권장합니다. `"throw"`는 다음 메이저 버전에서 기본값이 될 예정입니다. 여러 테넌트에 걸쳐 실행해야 하는 백그라운드 작업이라면 컨텍스트가 없는 경로에 의존하지 마세요. 대신 `runUnscoped()`, 명시적인 `run("public")`, `withoutTenantScope`, `@NonTenantEntity` 중 하나로 의도를 드러내세요.

### MySQL에서 `timestamptz`를 쓸 때

MySQL과 MariaDB에는 타임존 정보를 담는 `DATETIME` 타입이 없습니다. 그래서 `timestamptz` 컬럼은 일반 `DATETIME`으로 생성되고 오프셋은 저장되지 않습니다. 이 매핑은 1.x와 같습니다. 2.0부터는 프로세스당 한 번 경고를 남깁니다.

### 모르는 옵션 키

`register()`는 인식하지 못하는 옵션 키를 무시하지 않고 경고를 출력합니다. 경고에는 가장 비슷한 옵션 이름이 함께 나옵니다.

## 배포 파이프라인

### 마이그레이션 실패가 배포를 멈춥니다

`stingerloom migrate:run`과 `migrate:rollback`은 마이그레이션이 실패하면 종료 코드 1을 반환합니다. 1.x는 "0 succeeded, 1 failed"를 info 로그로 출력하고 종료 코드 0으로 끝났습니다. 그래서 `migrate:run && start` 같은 명령 체인이 마이그레이션이 절반만 적용된 스키마에서 그대로 앱을 시작했습니다.

배포 파이프라인을 한 번 확인해 보세요. 실패해도 성공으로 표시되던 잡이 이제 멈춥니다. 이것이 이 변경의 목적입니다. 다만 그동안 눈에 띄지 않게 실패하던 마이그레이션이 이번에 드러날 수도 있습니다.

인자 파서도 알 수 없는 플래그, 값이 빠진 옵션, 남는 인자를 버리지 않고 에러로 알립니다. 1.x에서는 `--dry-runn`을 무시한 채 파일을 생성했습니다. `--ouput ./migrations migrate:run`은 `./migrations`를 명령으로 실행했습니다.

### NestJS 종료 시 커넥션 풀

`StingerloomOrmService.onApplicationShutdown()`은 자신이 연 연결 풀을 모두 닫습니다. `tenantStrategy: "database"`로 만든 테넌트 풀도 모두 포함합니다. Nest의 셧다운 훅이 실행된 뒤에도 연결을 쓰는 코드는 이제 실패합니다. 그런 작업은 종료 전으로 옮기세요.

## 새 기능

아래 항목은 기존 코드를 깨뜨리지 않습니다. 2.0으로 올렸다면 도입해 볼 만합니다.

- **[쿼리 결과 캐시](./caching.md)**: 읽기마다 `cache: true`나 `cache: 30_000`으로 켭니다. 같은 `EntityManager`로 실행한 쓰기는 영향받는 테이블의 엔트리를 자동으로 무효화합니다.
- **[코드 우선 엔티티](./define-entity.md)의 상호 참조**: `defineEntity`로 만든 두 엔티티가 `TS7022` 순환 에러 없이 서로를 참조합니다.
- **타임존 교차 테스트**: 시각을 다루는 테스트가 있다면 `TZ` 하나에서만 실행하지 마세요. UTC에서는 타임존 표기 없이 저장한 값과 제대로 저장한 값이 똑같아 보입니다. 이번에 고친 버그도 모두 그 때문에 드러나지 않았습니다. Stingerloom 프로젝트는 `pnpm test:temporal-tz`로 네 개 타임존에서 테스트를 실행합니다.
